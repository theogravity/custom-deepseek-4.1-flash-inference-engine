# C4/C6 round three: host stalls and expert residency

Date: 2026-11-27. Workload: `tools/edit_scaling.py`, the 25,625-token Python edit, 1,500 generated tokens per client at temperature zero, one warm-up wave and six measured waves per client count. Each arm started a fresh server. Both inference GPUs were capped at 375 W. Rates are the `upstream_tok_s` median (the published vLLM convention); whole-wave medians are in the raw files. Every arm's reasoning and visible-output hashes matched the round's first control for every client.

| 4 | 518 | 499.2 | **533.9** | +7.0% | **+3.1%** |

The round-end row is the clean `ds4-flash-rs:tp2-round3-20261127` image with only the committed `compose.yml` and `tp2-prefill.yml` defaults. On the same host at 375 W, vLLM with CPU experts measured 537–561 at C6 ([same-host comparison](concurrent-edits.md)), so C6 is still behind it.

## What the profile showed

A 2.78 s Nsight Systems capture of a warm C6 wave (third wave after start, all six clients decoding) showed:

- Neither inference GPU ran a kernel for 34% of the window. Each GPU was busy for only 38–46% of it.
- The host spent 1.02 s in `cudaEventSynchronize` waiting for the per-layer router logits. This is the designed sync point.
- 8,498 synchronous `cudaMemcpy` calls in `ds_moe_run_dev` took 333 ms. Routed groups above 64 rows (every concurrent verification layer) skipped the inline descriptor path. Each copy waited for the device queue to drain.
- 637–952 expert uploads (13.27 MB each) took 265–335 ms of host time. The 68 GiB per-GPU cache holds about 71% of the 204 GB of routed target experts (40 layers × 384 experts).
- Smaller host round trips: rotary-table uploads in `device_freqs` (61 ms) and compressor D2H reads in `append_source` (73 ms).

The opt-in `DS4_STEP_TIMING=1` split of concurrent steps put the target forward at about 90% of host step time, drafting at about 7%, and scoring/commit at about 2.5%. Traces: `~/.cache/ds4-flash-rs/profiles/round3-20261127/` (`c6-trace.nsys-rep` sha256 `294d6f63…`, `bt.nsys-rep` with CUDA API backtraces, sha256 `f3f95111…`).

## Experiments

Each candidate was bracketed by controls. A candidate was kept only if it beat both neighbouring controls without lowering C4 or C6.

| # | Experiment | C4 (ctrl / cand / ctrl) | C6 (ctrl / cand / ctrl) | Decision |
|---|---|---|---|---|
| 1 | Inline MoE descriptors up to 256 rows (`DS4_MOE_INLINE_WIDE`) | 499.2 / **501.1** / 498.7; repeat 499.0 | 500.5 / **508.9** / 505.3; repeat 511.3 | Kept, default on |
| 2 | Pinned-ring async small H2D uploads (attention buffers, `to_device`), against both runs of #1 | 501.1, 499.0 / 503.9 | 508.9, 511.3 / **506.9** | Wash: C6 below both controls; reverted |
| 3 | Expert cache limit 88 GiB with a 4 GiB VRAM reserve (`DS4_MOE_HEADROOM_MIB`) | 499.0 / **535.0** / 500.5 | 511.3 / **533.3** / 507.5 | Kept, profile default |
| 3b | Same with a 6 GiB reserve | 503.8 | 523.9 | Not selected |

1. **Wide inline descriptors.** Routed groups of up to 256 rows now pass their jobs and rows as a 10 KiB `__grid_constant__` kernel parameter, as groups of up to 64 rows already did. This replaces two synchronous copies per group. The arithmetic is unchanged. C6 gained 0.7–1.7% and C4 was flat (+0.2–0.5%). The router sync still dominates each layer, so removing the extra drains recovers little. Set `DS4_MOE_INLINE_WIDE=0` to restore the copies.
2. **Async small uploads.** Copies of up to 64 KiB went through a 2 × 2 MiB pinned ring per device, reusing a half only after its completion event. The first run lost one stream. That code had a boundary bug (an exactly full half skipped its reuse wait), which was fixed before the measured run. The same incomplete-stream symptom has also appeared on unmodified builds ([prefix-fix report](prefix-fix-benchmark-20261127.md)). The fixed build matched every output but measured +0.6–1.0% at C4 and −0.4–0.9% at C6, so it was removed.
3. **Expert residency.** The cache already grows into free VRAM and gives slots back when KV, pooled buffers or attention scratch reserve memory. Its fixed 512 MiB reserve was the reason a larger limit was considered unsafe: an earlier 92 GiB trial left 1.1 GiB free. The new `DS4_MOE_HEADROOM_MIB` keeps a fixed amount of free VRAM outside the cache, for allocations that cannot reclaim slots (CUDA libraries, native scratch). With 88 GiB / 4 GiB the warm cache settles at about 78 GiB per GPU. Free VRAM stayed at 3.9–5.9 GiB through every decode run.

The 4 GiB vs. 6 GiB comparison shows a cliff. C4's four-edit working set fits at about 78 GiB of cache but not at 76, so C4 fell back to 503.8 with the 6 GiB reserve. Anything else that holds about 2 GiB more VRAM per GPU will remove most of the C4 gain.

## Cold prefill and memory check

Each configuration ran two warm C6 waves, then cold 189k- and 473k-token needle prompts with fresh seeds, then C6 waves again. Free VRAM was sampled every second. [Raw rows](../results/context/cold-after-decode-cache-88-vs-68-20261127.jsonl)

| | 68 GiB / 512 MiB | 88 GiB / 4 GiB |
|---|---:|---:|
| 189k cold TTFT | 95.9 s | 102.5 s |
| 473k cold TTFT | 149.6 s | 152.1 s |
| Needles | found | found |
| Lowest free VRAM, GPU 1 / GPU 2 | 2,660 / 4,704 MiB | 602 / 2,512 MiB |
| C6 waves after the long prompts | 141, 249, 277, 290 | 127, 256 |

There were no allocation failures. During the long prefills the new profile dipped 3.5 GiB below its reserve, to 602 MiB on GPU 1: non-reserving allocations still peak there. Cold TTFT changed by +7% and +2% on single samples.

Both configurations decode slowly for several waves after long cold prompts. This is pre-existing. A likely cause is LFU counts that accumulate over the process lifetime: prompt routing inflates the counts of the experts the prompt used, so decode-hot experts are evicted first. The cause turned out to be the prompt's rank shards inheriting decode counts; the fix is in [decode recovery after long prompts](expert-shard-eviction-20261127.md).

Not run: six concurrent 524k sessions, KV rotation and C1 with the new defaults.

## What limits C6 now

- **Stage-serial GPUs.** Layers 0–19 run on one card and 20–39 on the other. Only routed experts are split across both. A two-microbatch pipeline or true per-layer tensor parallelism would address this, at the cost of a scheduler rewrite.
- **Per-layer router sync.** Each layer's host top-k waits for the router logits, and the next layer's launches wait for the host. Removing it needs GPU routing and device-side expert placement.
- **Per-request attention launches.** `forward_group` runs each request's attention kernels serially, about six times the launches at C6.
